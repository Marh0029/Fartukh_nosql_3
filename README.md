# Частина 1 — Проєктування схеми
### ASCII-схема графа
(User)
  |
  | RATED
  | {rating, timestamp}
  v
(Movie)
  |
  | HAS_GENRE
  v
(Genre)

### Вузли

(User {userId, gender, age, occupation})
(Movie {movieId, title})
(Genre {name})

### Ребра

(User)-[:RATED {rating, timestamp}]->(Movie)
(Movie)-[:HAS_GENRE]->(Genre)

### 1. Які сутності стали вузлами, а які ребрами? Чому?

Користувачі, фільми та жанри були представлені як вузли, тому що вони є основними сутностями предметної області та мають власні властивості.

Оцінки стали ребрами між користувачами та фільмами, тому що вони описують взаємодію між двома сутностями.

Наприклад, користувач ставить оцінку певному фільму. Це природно представити як зв'язок між вузлами User і Movie.

### 2. Чому Rating — це ребро, а не окремий вузол?

Я обрала модель:

(User)-[:RATED]->(Movie),

тому що оцінка є відношенням між користувачем і фільмом. Переваги такого підходу у меншій кількості вузлів у графі,
простіших запитах та швидшому пошуку рекомендацій.

Недоліком є те, що оцінка не може легко мати власні складні зв'язки.

Для цього датасету окремий вузол Rating не потрібен, тому що оцінка має лише рейтинг і час.

### 3. Чому Genre краще зберігати окремим вузлом?

Якби жанри зберігались списком у Movie:

genres = ["Action","Comedy"]

то було б складніше знаходити всі фільми певного жанру або аналізувати популярність жанрів.

Окремі вузли Genre дозволяють легко знаходити всі фільми певного жанру, будувати рекомендації та виконувати графові алгоритми.

Тому модель:

(Movie)-[:HAS_GENRE]->(Genre)

є більш гнучкою.
# Частина 2 — Завантаження даних

### Users

LOAD CSV WITH HEADERS FROM 'file:///users.csv' AS row
MERGE (u:User {userId: toInteger(row.userId)})
SET u.gender = row.gender,
    u.age = toInteger(row.age),
    u.occupation = toInteger(row.occupation);

Створює вузли користувачів без дублювання.

### Movies + Genres

LOAD CSV WITH HEADERS FROM 'file:///movies.csv' AS row
MERGE (m:Movie {movieId: toInteger(row.movieId)})
SET m.title = row.title
WITH m, row
UNWIND split(row.genres, '|') AS genreName
MERGE (g:Genre {name: genreName})
MERGE (m)-[:HAS_GENRE]->(g);

Розбиває жанри на окремі вузли та зв’язує з фільмами.

### Ratings

CALL apoc.periodic.iterate(
'
LOAD CSV WITH HEADERS FROM "file:///ratings.csv" AS row
RETURN row
',
'
MATCH (u:User {userId: toInteger(row.userId)})
MATCH (m:Movie {movieId: toInteger(row.movieId)})
MERGE (u)-[r:RATED]->(m)
SET r.rating = toFloat(row.rating),
    r.timestamp = toInteger(row.timestamp)
',
{batchSize:10000, parallel:false}
);

Батчове завантаження для великих даних (щоб не впав Neo4j).

# Частина 3 — Запити

// Фільми жанру Thriller із середнім рейтингом > 4
MATCH (m:Movie)-[:HAS_GENRE]->(:Genre {name:'Thriller'})
MATCH ()-[r:RATED]->(m)
WITH m, avg(r.rating) AS avgRating
WHERE avgRating > 4
RETURN m.title, round(avgRating*100)/100 AS avgRating
ORDER BY avgRating DESC;

Запит знаходить усі фільми жанру Thriller та обчислює їх середній рейтинг на основі оцінок користувачів. За допомогою avg(r.rating) обчислюється середня оцінка кожного фільму. Після цього залишаються лише ті фільми, середній рейтинг яких перевищує 4.0. Результати сортуються за спаданням рейтингу, щоб найкраще оцінені фільми були показані першими.

// Користувачі, які поставили 5 більше ніж 50 фільмам
MATCH (u:User)-[r:RATED]->()
WHERE r.rating = 5
WITH u, count(r) AS fiveStars
WHERE fiveStars > 50
RETURN u.userId, fiveStars
ORDER BY fiveStars DESC;

Запит знаходить користувачів, які часто ставлять максимальну оцінку. Спочатку вибираються всі зв'язки RATED з рейтингом 5. Потім для кожного користувача підраховується кількість таких оцінок. У результат потрапляють лише користувачі, які поставили оцінку 5 більш ніж 50 разів. Це дозволяє виявити найбільш активних або найбільш позитивно налаштованих користувачів.

// Фільми, які високо оцінили User 1 та User 2
MATCH (u1:User {userId:1})-[r1:RATED]->(m:Movie)
MATCH (u2:User {userId:2})-[r2:RATED]->(m)
WHERE r1.rating >= 4
  AND r2.rating >= 4
RETURN m.title,
       r1.rating AS user1Rating,
       r2.rating AS user2Rating;

Запит знаходить фільми, які обидва користувачі оцінили позитивно (рейтинг не менше 4). Для кожного такого фільму повертається його назва та оцінки обох користувачів. Це дозволяє визначити спільні вподобання користувачів та є основою для побудови рекомендаційних систем.

// Жанри з високими рейтингами
MATCH (m:Movie)-[:HAS_GENRE]->(g:Genre)
MATCH ()-[r:RATED]->(m)

WITH g,
     avg(r.rating) AS avgRating,
     count(r) AS ratingsCount

RETURN g.name,
       round(avgRating*100)/100 AS avgRating,
       ratingsCount
ORDER BY avgRating DESC;

Запит аналізує рейтинги на рівні жанрів. Для кожного жанру обчислюється середній рейтинг усіх фільмів цього жанру та загальна кількість отриманих оцінок. Це дозволяє визначити, які жанри користуються найкращою оцінкою серед користувачів, а також оцінити популярність жанру за кількістю рейтингів.

### Що означає довжина шляху?

Довжина шляху показує кількість ребер між вузлами.
## Шлях довжини 2
User -> Movie <- User

означає, що два користувачі оцінили один і той самий фільм.

## Шлях довжини 4
User -> Movie <- User -> Movie <- User

означає, що користувачі пов'язані через іншого користувача та спільні фільми.

## Шлях довжини 6
User -> Movie <- User -> Movie <- User -> Movie <- User

означає ще більш непрямий зв'язок між користувачами через декілька спільних переглядів.

Чим коротший шлях, тим більш схожими можуть бути користувачі.


# Частина 4 — Супервузли

// Знайти вузли з найбільшою кількістю зв'язків

MATCH (n)-[r]-()
WITH n, count(r) AS degree
RETURN
labels(n) AS nodeType,
coalesce(n.title, n.name, toString(n.userId)) AS node,
degree
ORDER BY degree DESC
LIMIT 20;

Запит знаходить вузли з найбільшою кількістю зв'язків у графі. Для кожного вузла підраховується його степінь (degree) — кількість інцидентних ребер. Результати сортуються за спаданням кількості зв'язків. Такий аналіз дозволяє виявити супервузли (supernodes), які можуть негативно впливати на продуктивність запитів через дуже велику кількість зв'язків.

### 1. Які вузли стали супервузлами?

Супервузол (supernode) — це вузол з дуже великою кількістю зв'язків у порівнянні з іншими вузлами графа.

Супервузлами стали популярні movies (наприклад, Toy Story) та активні users.

Також деякі популярні фільми мають тисячі оцінок користувачів.

### 2. Чому запити працюють повільніше?

Коли запит потрапляє на супервузол, Neo4j змушений переглядати дуже велику кількість зв'язків.

Наприклад, якщо жанр Drama має тисячі фільмів, то система повинна пройти через усі ці зв'язки.

Тому навіть за наявності індексів такі запити працюють повільніше.

### 3. Яку стратегію можна застосувати?

Для цього датасету варто обмежувати обходи через супервузли. Наприклад, використовувати фільтрацію за рейтингом, працювати лише з популярними зв'язками та створювати окремі проєкції для GDS.

Також жанри можна використовувати лише для аналітики, а не для довгих обходів графа.

# Частина 5 — GDS

### 5.1 PageRank (Movie Graph)
Проєкція + алгоритм
CALL gds.graph.project(
  'movieGraph',
  'Movie',
  {
    CO_RATED: {
      orientation: 'UNDIRECTED',
      properties: 'weight'
    }
  }
);

Цей запит створює віртуальний граф у пам’яті GDS, де вузли = фільми (Movie), а ребра = зв’язки між фільмами, які часто оцінювали одні й ті самі користувачі (CO_RATED). Weight показує силу зв’язку (скільки користувачів оцінили обидва фільми високо). Тобто ми будуємо мережу схожості між фільмами.

### PageRank запуск
CALL gds.pageRank.stream('movieGraph')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).title AS movie,
       score
ORDER BY score DESC
LIMIT 10;

Цей запит запускає алгоритм PageRank на графі фільмів. Він визначає, наскільки “важливий” кожен фільм у мережі.

### Що означає високий PageRank?

Високий PageRank означає, що фільм не просто популярний, а “центральний у мережі спільних високих оцінок”.
Це фільми, які часто оцінюють високо ті самі користувачі, що й інші важливі фільми.

Тобто це не просто “багато оцінок”, а вплив у структурі смаків. 

### 5.2 Louvain (спільноти користувачів)

CALL gds.louvain.stream('userSimilarity')
YIELD nodeId, communityId
RETURN communityId,
       count(*) AS size
ORDER BY size DESC
LIMIT 10;

Запит знаходить спільноти користувачів. Користувачі групуються в кластери. Якщо вони ставлять оцінки одним і тим самим фільмам — вони потрапляють в одну спільноту


### Аналіз жанрів по спільноті
MATCH (u:User)-[:RATED]->(m:Movie)-[:HAS_GENRE]->(g:Genre)
WHERE u.communityId IS NOT NULL
WITH u.communityId AS community, g.name AS genre, count(*) AS cnt
WITH community, genre, cnt,
     row_number() OVER (PARTITION BY community ORDER BY cnt DESC) AS rn
WHERE rn <= 3
RETURN community, genre, cnt
ORDER BY community, cnt DESC;

Цей запит аналізує які жанри домінують у кожній спільноті.

### 5.3 Найкоротший шлях (Dijkstra)

Проєкція графа користувачів
CALL gds.graph.project(
  'userGraph',
  'User',
  {
    SIMILAR: {
      orientation: 'UNDIRECTED',
      properties: 'weight'
    }
  }
);


Код створює граф, де вузли = користувачі, 
ребра = схожість між користувачами (SIMILAR), а  вага = наскільки схожі їхні смаки

### Найкоротший шлях (Dijkstra)

MATCH (start:User {userId: 1}), (end:User {userId: 10})

CALL gds.shortestPath.dijkstra.stream('userGraph', {
  sourceNode: id(start),
  targetNode: id(end),
  relationshipWeightProperty: 'weight'
})
YIELD totalCost, nodeIds
RETURN totalCost,
       [nodeId IN nodeIds | gds.util.asNode(nodeId).userId] AS path;

Цей запит знаходить найкоротший “шлях схожості” між двома користувачами. Алгоритм Dijkstra шукає найменш “дорогий” шлях у графі

### Що означає високий PageRank?

Високий PageRank означає, що фільм не просто популярний, а “центральний у мережі спільних високих оцінок”.
Це фільми, які часто оцінюють високо ті самі користувачі, що й інші важливі фільми.

Тобто це не просто “багато оцінок”, а вплив у структурі смаків

### Чи відповідають кластери інтуїції?

Частково так. Спільноти формуються не напряму по жанрах, а через схожість оцінок, тому всередині кластерів можуть домінувати певні жанри (наприклад, Action або Drama), але вони не є “чистими групами”.

### Як перевіряли?

Через аналіз топ жанрів у кожній спільноті та порівняння частоти оцінок фільмів різних жанрів.

### Наскільки “тісний світ”?

У датасеті спостерігається ефект small-world: більшість користувачів з’єднані через 2–4 кроки.

### Чи підтверджується 6 рукостискань?

Так, але навіть сильніше — більшість шляхів значно коротші за 6.


# Частина 6 — Аналіз та висновки

### 1. Graph vs SQL

Графова база даних добре працює для пошуку зв'язків між об'єктами. Наприклад, запит "користувачі зі схожими смаками також дивилися" дуже природно реалізується через граф.

У SQL довелося б використовувати багато JOIN.

Приклад SQL:

SELECT DISTINCT m2.movieId
FROM ratings r1
JOIN ratings r2
ON r1.movieId = r2.movieId
AND r1.userId <> r2.userId
JOIN ratings r3
ON r2.userId = r3.userId
JOIN movies m2
ON r3.movieId = m2.movieId;

Такий запит стає складним і повільним. У Neo4j це виконується значно простіше через обходи графа.

### 2. Де граф програє?

Реляційні бази краще підходять для звітності, агрегування, статистики та експорту даних.

Наприклад, середній рейтинг усіх фільмів або топ-10 жанрів.

Такі запити SQL виконує дуже швидко. Для масових агрегацій реляційна модель ефективніша.

### 3. Як можна покращити схему?

Для рекомендацій можна створити зв'язки:

(User)-[:SIMILAR]->(User)

Тоді рекомендації будуть виконуватись швидше.

Для аналізу фільмів можна створити зв'язки:

(Movie)-[:CO_RATED]->(Movie)

між фільмами, які часто високо оцінювали одні й ті самі користувачі.

Тоді PageRank та інші алгоритми працюватимуть швидше.

Створення precomputed relationships:

(User)-[:SIMILAR]->(User)
(Movie)-[:CO_RATED]->(Movie)

зменшує runtime для GDS, прибирає дорогі traversal запити та покращує рекомендації
